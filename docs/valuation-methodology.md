# Методология оценки стартапов

Документ фиксирует, как DevStart считает диапазон оценки (pre-money, ₽) и откуда берёт рыночные
данные. Цель — **прозрачность методологии** и **воспроизводимость** оценок задним числом.

## Ансамбль методов

Оценка — взвешенный ансамбль из четырёх методов; веса ренормируются к сумме 1.0 по методам, которые
реально участвуют на данной стадии. Версия методологии (`MethodologyVersion`) едет на каждом
результате и снапшоте.

| Метод | Что считает | Стадии применимости |
|---|---|---|
| **Berkus** | 5 факторов (idea, prototype, team, partnerships, traction) × ₽-потолок | Idea, PreSeed, Mvp |
| **Scorecard** | медиана pre-money (по сектору/стадии) × Σ(весᵢ × множительᵢ) | Idea, PreSeed, Mvp, Seed — **нужна медиана** |
| **VC Method** | TV = exit-revenue × отраслевой множитель; post = TV / (1+IRR)ⁿ | Mvp, Seed, SeriesA |
| **Comparable** | отраслевой мультипликатор выручки × ARR | Mvp, Seed, SeriesA — **нужны мультипликатор и ARR > 0** |

Диапазон: `Low = min(point×(1−band), minMethod)`, `High = max(point×(1+band), maxMethod)`; гарантируется
`Low ≤ Point ≤ High`. Если ни один метод не применим — явный сигнал «недостаточно данных» (пустой
`MethodsUsed`, нулевой диапазон), а не сфабрикованный ₽0.

## Источник данных бенчмарков

Медианы pre-money и мультипликаторы выручки — **данные, а не код**. Они лежат в таблице
`valuation_benchmark` и читаются движком через `IValuationBenchmarkProvider`. Это позволяет обновлять
рынок без релиза.

- **Наполнение** — через админский API (`/api/admin/valuation-benchmarks`, право
  `admin_valuation_benchmarks::manage`). У каждой записи **обязателен `source`** (например, «Dsight 2025
  Annual» + ссылка) и фиксируется автор (`created_by`).
- **Гранулярность.** Медиана — по паре (сектор, стадия); для общей медианы используется сектор `Other`
  как fallback. Мультипликатор — по сектору (без разреза по стадии).
- **Ритм обновления — квартал.** Данные крошечные и редко меняются, поэтому весь набор кэшируется
  (Redis); запись через админ-API инвалидирует кэш.

### Версионирование и воспроизводимость

Каждая строка имеет `effective_from`. При расчёте берётся **последняя версия с `effective_from ≤ дате
оценки`**, будущие версии игнорируются. Это даёт воспроизводимость: оценку прошлым числом можно
повторить на тех данных, что действовали тогда.

### Правки — только версионированием (append-only)

Записи **не редактируются и не удаляются**. Корректировка — это **новая строка** с более поздним
`effective_from`; старые версии остаются в истории (`/api/admin/valuation-benchmarks/history`). Так
история бенчмарков неизменна, а воспроизводимость задним числом не ломается.

### Поведение «недостаточно данных»

Hardcoded-fallback убран. Если на (сектор, стадию) нет медианы — **Scorecard не участвует** в ансамбле;
если на сектор нет мультипликатора или у стартапа нет выручки (`ARR = 0`) — **Comparable не участвует**.
Веса оставшихся методов ренормируются. Пример: на Idea/PreSeed без медианы остаётся Berkus.

ARR для методов оценки считается **только от настоящей метрики MRR** (MRR × 12). Метрика `Revenue`
(период не определён) используется лишь как прокси для **балла Traction** и в ARR не попадает — стартап
без MRR-метрики для Comparable/VC считается pre-revenue, а не получает завышенный ×12 якорь выручки.

## Сид

Начальные медианы (Idea/PreSeed/Mvp/Seed для сектора `Other`, `source = "initial seed"`) засеваются на
старте, чтобы движок не остался без медиан в день релиза. Мультипликаторы не сидируются — они вносятся
через админ-API после первого квартального наполнения.

## Форвард-нота: вариант E (overlay на собственных данных)

Когда по ячейке (сектор/стадия) накопится достаточно собственных наблюдений, медиана может частично
смещаться к собственным данным. Параметр перехода зафиксирован как **N = 10** (порог числа наблюдений).
Сам overlay в текущем объёме **не реализован** — заложена только совместимость: он встраивается **за
`IValuationBenchmarkProvider`**, без изменения самих методов оценки (Scorecard/Comparable читают набор
бенчмарков как и сейчас).
